# Purple Team: Account Creation and Privilege Escalation for Persistence (T1136.002 / T1098)

**MITRE ATT&CK:**
[T1136.002 — Create Account: Domain Account](https://attack.mitre.org/techniques/T1136/002/) ·
[T1098 — Account Manipulation](https://attack.mitre.org/techniques/T1098/)

## Goal

Purple teaming tests whether an attack is actually visible to my monitoring, and where
the gaps are. This exercise looks at a classic post-compromise move: an attacker who has
gained control of a domain controller creates a new account and adds it to Domain Admins,
giving them privileged persistence that survives even if the original entry point is
closed. I wanted to know whether my monitoring would catch that, and to build the
detections to close whatever gaps I found.

## Hypothesis

Creating a domain account and adding it to a privileged group will generate specific
Windows Security events: 4720 (account created) and 4728 (member added to a global group).
A detection should alert on new account creation, on additions to Domain Admins, and
ideally on the two happening together in a short window, which is the strongest signal.

## Scenario

**Assumed breach.** An attacker has compromised the domain controller (or a privileged
account on it). Wanting to keep access, they create a new account they control and
elevate it to Domain Admin. This is a common, realistic persistence-plus-privilege move,
and a rogue Domain Admin account is about as strong a foothold as an attacker can have.

## Environment

- **Domain Controller:** Windows Server 2025 (Windows_Server_2025.LCSL.com), acting as the
  compromised host
- **SIEM:** Splunk, with the Windows event logs forwarded from the DC
- **Attack run from the DC itself**, modelling the compromise

## What I'm testing

1. **Is the activity logged?** Does the DC record account creation (4720) and group
   changes (4728) when the attack runs?
2. **Can I detect it?** If the events are there, can I build detections that catch the
   technique reliably, including the create-then-elevate sequence?

## Method and findings

### Baseline

Before the attack, a search for account-creation events returned nothing:

    host="Windows_Server_2025" source="WinEventLog:Security" EventCode=4720 | stats count

Zero events. That was the first sign something was off, since account creation should log.

### Gap 1 — account-management auditing was disabled

I ran the attack from the DC:

    net user backdoor Password123! /add /domain
    net group "Domain Admins" backdoor /add /domain

    ![alt text](<Screenshot 2026-09-10 183716.png>)

Both commands succeeded, so the account was created and added to Domain Admins. But the
search still returned no 4720 events. Listing every event code present on the DC confirmed
it: 4720 (account created) and 4728 (group member added) were nowhere in the data.

**Finding:** account-management auditing wasn't enabled on the DC at all. Windows wasn't
generating the events, so nothing downstream could ever detect account creation or group
changes — a blind spot for one of the most common persistence techniques there is.

Fixed by enabling the relevant audit subcategories on the DC:

    auditpol /set /subcategory:"User Account Management" /success:enable /failure:enable
    auditpol /set /subcategory:"Security Group Management" /success:enable /failure:enable

Verified with `auditpol /get`, then deleted and re-ran the attack so the events would
generate with auditing now on. This time the 4720 and 4728 both landed in Splunk.

### Gap 2 — the account name wasn't extracted into a usable field

With the events flowing, I hit a second problem building the correlation rule. The account
name is in the raw event text but not extracted into a clean, searchable field, and worse,
it's logged in *different formats* across the two event types:

- **4720 (create):** the account appears as a plain name — `Account Name: backdoor`
- **4728 (group add):** the same account appears as a full Distinguished Name —
  `Account Name: CN=backdoor,CN=Users,DC=LCSL,DC=com`

So the same logical entity is represented two different ways, and neither is a ready-made
field. To correlate the two events on the account, I had to extract and normalise the name
myself with `rex`, pulling just the CN out of the DN so it matches the plain name from the
4720:

    | rex "Member:\s+Security ID:\s+\S+\s+Account Name:\s+CN=(?<member_account>[^,]+)"
    | rex "New Account:\s+Security ID:\s+\S+\s+Account Name:\s+(?<target_account>\S+)"
    | eval account=coalesce(target_account, member_account)

This is a good example of detection engineering being more about data normalisation than
detection logic: the hard part wasn't the rule, it was getting the account name into a
consistent form across two event types.

### Gap 3 — a logic error in the correlation

My first attempt at the create-then-elevate correlation used `stats min/max` to measure the
time between events:

    | stats min(_time) as first_seen, max(_time) as last_seen, dc(EventCode) as code_count by account
    | where code_count=2 AND (last_seen - first_seen) < 300

It never fired, even though the create and elevate were seconds apart. The reason was a
genuine logic error: `stats min/max by account` collapses *every* event for that account
into one row and measures the span from the earliest to the latest. Across my repeated
test runs, that span was ~14 minutes, so it failed the 5-minute window even though each
individual create-elevate pair was ~2 seconds apart. The query was measuring the wrong
thing entirely.

Fixed by switching to `transaction`, which groups events into discrete sequences that
occur close together in time rather than collapsing all of them:

    | transaction account maxspan=5m
    | where eventcount>=2 AND mvcount(mvdedup(EventCode))>=2

This correctly grouped each create-then-elevate as its own transaction. The test attack
showed as a single sequence spanning **2.24 seconds** from account creation to Domain
Admin membership.

### Tuning note — multiple events per action

Testing also showed that a single `net group /add` generates several 4728 events (one
logical action, multiple log entries as the directory change is recorded). So the alerts
key on "results greater than zero" and trigger once per run rather than per event, so one
attack produces one alert rather than flooding an analyst with duplicates.

## Detections

Three detections, escalating in fidelity.

**1. New domain account created (T1136.002)**

    host="Windows_Server_2025" source="WinEventLog:Security" EventCode=4720
    | table _time, Account_Name

Flags every new domain account for review. Catches account creation even for a low-priv
account an attacker might use quietly.

**2. Account added to Domain Admins (T1098)**

    host="Windows_Server_2025" source="WinEventLog:Security" EventCode=4728 "Domain Admins"
    | table _time, Account_Name

Flags any addition to Domain Admins. This catches privilege escalation including an
*existing* account being elevated, which the account-creation rule alone would miss.
Additions to Domain Admins are rare and high-impact, so every one is worth reviewing.

**3. Account created and elevated within 5 minutes (T1136.002 / T1098)**

    host="Windows_Server_2025" source="WinEventLog:Security" (EventCode=4720 OR EventCode=4728)
    | rex "Member:\s+Security ID:\s+\S+\s+Account Name:\s+CN=(?<member_account>[^,]+)"
    | rex "New Account:\s+Security ID:\s+\S+\s+Account Name:\s+(?<target_account>\S+)"
    | eval account=coalesce(target_account, member_account)
    | transaction account maxspan=5m
    | where eventcount>=2 AND mvcount(mvdedup(EventCode))>=2
    | eval window_seconds = duration
    | table account, EventCode, window_seconds

The high-fidelity one. A brand-new account becoming Domain Admin within minutes is almost
never legitimate, so correlating the two events makes for a strong, low-false-positive
signal. The test attack fired it with a 2.24-second window.

All three were deployed as scheduled alerts running every 10 minutes, with the search
window matched to the run interval (last 10 minutes) so events aren't double-counted
across overlapping windows, and the windows snapped to minute boundaries to keep
consecutive runs contiguous.

## False positives

- **Legitimate account creation and admin onboarding** — IT creates accounts and adds
  people to groups as normal business. Rule 1 will fire on all of it, so it's an
  alert-and-review rule rather than a high-severity page; in production you'd allowlist
  known admin accounts doing the creating.
- **Service account provisioning** — automated systems creating accounts. Same handling:
  allowlist known service/provisioning accounts.
- **Additions to Domain Admins (Rule 2)** are rare enough that a false positive is itself
  worth reviewing — an unexpected legitimate addition to Domain Admins is a governance
  issue in its own right.
- **Rule 3 is the most robust** — the tight create-then-elevate window makes a legitimate
  match very unlikely, since normal onboarding doesn't create an account and make it Domain
  Admin in the same couple of minutes.

## Outcome

I started with no visibility of this technique at all: the DC wasn't auditing account
management, so account creation and group changes were completely invisible to the SIEM. I
finished with auditing enabled, the events flowing and parsed, and three working detections
covering the technique from account creation through privilege escalation to the full
create-then-elevate sequence. Along the way I hit and fixed a real correlation logic error
and a field-normalisation problem, both of which are good reminders that detection
engineering is often more about the data than the detection.

The rogue account was removed after testing.
